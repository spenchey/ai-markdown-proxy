# Transaction security contract

Status: mandatory gate for any future service or parts mutation

## Boundary

No scheduling, parts, order, cancellation, or payment tool may be exposed until its authoritative vendor contract passes the integration proof gate. Public DealerOn forms and reverse-engineered browser endpoints are not supported transaction APIs.

The protected transaction gateway must be operationally separate from the public AI mirrors. Anonymous inventory and dealership reads may remain public; customer-owned data and mutations require delegated customer identity.

## State invariant

The gateway must preserve these meanings:

- `requested`: a lead, contact request, or operation request was accepted, but the system of record did not confirm the business transaction;
- `held`: the system of record created an expiring provisional reservation and returned its hold identifier and expiration;
- `confirmed`: the authoritative scheduler or commerce system returned its durable confirmation or order receipt;
- `cancelled`: the authoritative system accepted the cancellation and returned its receipt;
- `failed`: no valid state transition occurred.

Neither an HTTP success code from the gateway nor a successful form submission is sufficient evidence for `confirmed`.

## OAuth and identity requirements

- OAuth protected-resource metadata per RFC 9728.
- OAuth resource indicators per RFC 8707; tokens are audience-bound to the exact gateway resource.
- Authorization Code with PKCE for delegated customer actions.
- No token passthrough to downstream systems.
- Short-lived access tokens and rotated refresh tokens where supported.
- Step-up scopes immediately before consequential operations.
- Explicit separation of these minimum scopes:
  - `inventory.read`
  - `service.availability.read`
  - `service.appointment.read`
  - `service.appointment.create`
  - `service.appointment.reschedule`
  - `service.appointment.cancel`
  - `parts.catalog.read`
  - `parts.cart.write`
  - `parts.order.create`
  - `parts.order.read`
  - `parts.order.cancel`
- Customer ownership checks on every protected read and write.
- Rooftop authorization is explicit; a token for one rooftop does not grant another.

## Approval contract

Every create, reschedule, cancellation, order, and payment operation requires an approval record bound to the final normalized payload.

The approval record contains:

- delegated customer identity;
- agent client identity;
- operation and scope;
- rooftop/location;
- final appointment slot or order line items;
- final totals, fees, taxes, delivery/pickup terms, and cancellation policy where applicable;
- human-readable review text shown to the customer;
- hash of the normalized payload;
- approval timestamp and expiration;
- single-use nonce.

Changing a material field invalidates the approval and requires a new review.

## Idempotency contract

- Every mutation requires an `Idempotency-Key` generated by the client and scoped to customer, operation, and resource server.
- The gateway stores the normalized request hash, downstream request identifier, current state, response body, and retention expiration.
- Repeating a key with the same normalized request returns the stored result.
- Repeating a key with a different normalized request returns a conflict and performs no downstream call.
- A timeout after downstream submission enters `outcome_unknown`; the gateway retrieves authoritative state before retrying.
- Automatic retries are bounded and never issue a second create while the first outcome is unknown.

## Receipt contract

A successful mutation response contains:

- gateway request ID;
- idempotency key;
- agent client and delegated customer identifiers;
- rooftop/location;
- authoritative system name;
- authoritative confirmation, hold, order, or cancellation identifier;
- authoritative state;
- source-system timestamp;
- normalized payload hash;
- approval record ID;
- links or instructions for customer verification and human support.

If the downstream system returns no durable identifier, the gateway may return `requested` or `outcome_unknown`, never `confirmed`.

## Audit and privacy contract

- Append-only audit events for authorization, approval, tool invocation, downstream request, downstream response classification, state transition, retry suppression, and human override.
- PII, access tokens, payment credentials, and raw vendor payloads are redacted from application logs.
- Audit access is separately authorized and recorded.
- Retention is purpose-limited and documented by data class.
- Customer deletion and correction workflows identify which source system remains authoritative.
- No customer data enters public AI-mirror caches, search corpora, sitemaps, or telemetry.

## Failure and isolation tests

Production approval requires evidence for:

1. duplicate create requests with the same key;
2. conflicting payload reuse of one key;
3. gateway timeout before and after downstream acceptance;
4. stale or disappeared appointment slot;
5. price, tax, or stock change after approval;
6. wrong-customer appointment/order read;
7. wrong-rooftop access;
8. scope escalation and token audience mismatch;
9. prompt/tool/output injection in upstream content;
10. misleading tool descriptions or ambiguous “finalize” actions;
11. unauthorized reschedule, cancellation, order, or refund;
12. downstream partial failure and reconciliation;
13. audit-log redaction and completeness;
14. safe customer handoff when the authoritative system is unavailable.

No single HTTP 200, UI screenshot, unit test, or vendor ticket proves this contract. The release evidence must include a bounded end-to-end operation against the actual source of record and its final receipt.
